## 1. ЦЕЛЬ ПРОЕКТА

Автоматизированный AI-сервис обработки длинных видео, Twitch VOD, YouTube-видео и локальных файлов.

Система получает длинное видео и самостоятельно выполняет:

| № | Задача | Приоритет |
|---|---|---|
| 1 | Анализ видео и аудио | высокий |
| 2 | Распознавание речи (русский, английский, автоопределение языка) | высокий |
| 3 | Определение интересных моментов | **ключевой** |
| 4 | Самостоятельное определение начала и конца момента | **ключевой** |
| 5 | Удаление тишины, пауз, загрузок, повторов | высокий |
| 6 | Вертикальные ролики 9:16 для TikTok / Shorts / Reels | высокий |
| 7 | Автовыбор области кадра, работа с вебкамерой | высокий |
| 8 | Субтитры с потайминговкой отдельных слов | высокий |
| 9 | Длинные компиляции для YouTube | средний |
| 10 | Генерация названия | средний |
| 11 | Генерация описания | средний |
| 12 | Генерация хэштегов | средний |
| 13 | Автопубликация на платформы | низкий |
| 14 | Анализ статистики опубликованного и улучшение выбора моментов | средний, см. [§63](#63-сбор-данных-о-результатах-клипов) |
| 15 | Публичный сервис по подписке | отложено, см. [docs/BACKLOG-legal.md](docs/BACKLOG-legal.md) |

Главная идея:

> Не «нарезчик видео», а AI-монтажёр, который получает 5–10 часов стрима и самостоятельно превращает его в набор качественных вирусных Shorts и длинных YouTube-компиляций, как у нарезчиков популярных стримеров.

## 2. ОСНОВА ПРОЕКТА

Исходный проект: <https://github.com/SamurAIGPT/AI-Youtube-Shorts-Generator> (MIT).

**Решение: репозиторий используется как справочник, форк не делается.**

Обоснование — фактическое состояние репозитория на момент аудита:

| Что предполагалось переиспользовать | Факт |
|---|---|
| Загрузка видео, yt-dlp | Есть, но это тонкая обёртка |
| FFmpeg | Есть, простая нарезка |
| Структура pipeline | Линейный CLI-скрипт без очереди, БД и восстановления после сбоя — под 8-часовые VOD не подходит |
| Frontend / backend | **Отсутствуют.** Только CLI `main.py` |
| Базовый поиск клипов | LLM читает весь транскрипт и выдаёт таймкоды — ровно то, что запрещает [§39](#39-нельзя-делать) |
| Экспорт видео | Примитивный, без субтитров и нормализации громкости |

Что взять оттуда как знание (см. `docs/upstream-notes.md`):

- таксономия виральности: hook / emotional peak / opinion / revelation / conflict / quotable line / story arc / practical value;
- чанкинг длинного транскрипта окнами 1200 с с перекрытием 60 с;
- дедупликация кандидатов по перекрытию >50% с выбором по score;
- предварительная классификация типа контента для подстройки промпта — расширить на «гейминг / just chatting / IRL»;
- сглаживание движения при face tracking.

**Про платный API.** Речь о **MuAPI** — сервисе автора, включённом в исходном проекте по умолчанию (`--mode api`). Мы его не используем. Это **не** запрет на коммерческие LLM API вообще: они остаются опциональными, см. [§25](#25-llm) и [§29](#29-режимы-стоимости).

## 4. ОБЩАЯ АРХИТЕКТУРА

Ключевой принцип: **стоимость стадии растёт по мере сужения материала.** Дорогие операции никогда не выполняются по всему VOD.

```text
                                          объём обработки
INPUT                                     ─────────────────
  ↓
VIDEO INGESTION                           весь VOD
  ↓
AUDIO EXTRACTION                          весь VOD
  ↓
SPEECH-TO-TEXT + WORD TIMESTAMPS          весь VOD   (GPU, дорого по времени)
  ↓
ДЕШЁВЫЕ СИГНАЛЫ                           весь VOD   (CPU, дёшево)
  ├── AUDIO ANALYSIS (громкость, теги)
  ├── SCENE DETECTION
  ├── TWITCH CHAT (если есть)
  └── VAD / паузы
  ↓
CANDIDATE CLIP DETECTION                  → 100–200 окон
  ↓
LLM SEMANTIC ANALYSIS                     только кандидаты
  ├── оценка интересности
  └── УТОЧНЕНИЕ ГРАНИЦ (start/end)        ← здесь, не позже
  ↓
CLIP SCORING                              после уточнения границ
  ↓
TOP-N SELECTION                           → 10–30 клипов
  ↓
UNWANTED CONTENT REMOVAL                  только выбранные   → формирует EDL (§56)
  ↓
VERTICAL VIDEO TRACKING / CV              только выбранные   (GPU, дорого)
  ↓
SUBTITLE GENERATION                       только выбранные   (через EDL)
  ↓
SHORT GENERATION  ·  LONG COMPILATION
  ↓
TITLE / DESCRIPTION / HASHTAGS
  ↓
EXPORT
  ↓
OPTIONAL PUBLISHING
```

**Два изменения относительно v1, обоснование:**

1. **CV перенесён вниз.** В v1 компьютерное зрение стояло до отбора кандидатов, то есть прогонялось по всем 8 часам. Это самая дорогая операция в проекте, и её результат для ~98% хронометража выбрасывается. Теперь трекинг работает только по выбранным клипам.
2. **Уточнение границ перенесено вверх, в стадию LLM.** В v1 `START/END REFINEMENT` стоял после `CLIP SCORING`, из-за чего score считался по неуточнённым границам и после сдвига становился недействительным. Границы — смысловая задача ([§14](#14-поиск-начала-клипа), [§15](#15-поиск-конца-клипа)), их определяет LLM, и score считается уже по финальным границам.

## 5. INPUT

Поддерживаемые источники:

- **YouTube** — URL
- **Twitch** — VOD URL (и чат к нему, [§41](#41-twitch-chat))
- **Локальный файл** — MP4, MKV, MOV, WEBM и всё, что читает FFmpeg

Использовать yt-dlp там, где это возможно и законно. Не обходить DRM, приватный доступ и другие технические ограничения.

Правовая сторона (права на контент, retention, DMCA) вынесена в [docs/BACKLOG-legal.md](docs/BACKLOG-legal.md) и открывается до публичного запуска. В схему БД **сейчас** закладываются два поля, чтобы потом не мигрировать: источник контента (свой / чужой) и срок хранения.

## 6. СКАЧИВАНИЕ

Инструменты: `yt-dlp`, `FFmpeg`.

Downloader обязан:

1. получить URL;
2. определить тип источника;
3. скачать видео;
4. сохранить metadata и исходный URL;
5. определить длительность, FPS, разрешение;
6. извлечь аудио (16 кГц моно для STT, отдельно от исходной дорожки).

Каждому исходному видео присваивается уникальный ID. Раскладка файлов — единая, описана в [§32](#32-storage). В v1 здесь была вторая, несовместимая схема; она удалена.

## 7. SPEECH-TO-TEXT

Основа: **WhisperX** (<https://github.com/m-bain/whisperX>, BSD-2-Clause), поверх `faster-whisper` / CTranslate2.

Требования: русский, английский, автоопределение языка, timestamps, **word-level timestamps**, VAD, опциональная диаризация.

Результат — структурированный JSON:

```json
{
  "language": "ru",
  "segments": [
    {
      "start": 120.52,
      "end": 124.81,
      "text": "Это был невероятный момент",
      "words": [
        { "word": "Это", "start": 120.52, "end": 120.80 },
        { "word": "был", "start": 120.82, "end": 121.10 }
      ]
    }
  ]
}
```

Данные используются для субтитров, анализа, поиска границ клипов, удаления тишины, генерации текста и определения структуры разговора.

**Важное ограничение по русскому языку.** Word-level timestamps в WhisperX делаются отдельной моделью выравнивания. Штатные модели torchaudio есть только для `{en, fr, de, es, it}`; русский идёт через `DEFAULT_ALIGN_MODELS_HF` (wav2vec2 xlsr-53-russian, Apache-2.0), и качество выравнивания заметно ниже английского — особенно на числах, англицизмах и игровом сленге. Это напрямую влияет на [§18](#18-субтитры). План Б: word timestamps самого faster-whisper как запасной путь, с возможностью переключения в конфиге.

Отдельно и обязательно: фильтрация галлюцинаций, см. [§57](#57-надёжность-stt).

## 8. SPEAKER DIARIZATION

`pyannote.audio` — по необходимости, не в MVP.

Система должна связывать речь с участниками (`SPEAKER_01`, `SPEAKER_02`, …), для Twitch это особенно важно:

```text
Streamer: «Сейчас я попробую...»
Друг:     «Не делай этого!»
Streamer: «Да ладно!»
```

Практические оговорки:

- на игровом звуке (игра + музыка + голоса в Discord) точность заметно ниже, чем на подкастах;
- прогон по всем 8 часам долгий и в основном бесполезен → запускать **только по речевым участкам либо только по кандидатам**;
- модель gated: нужен HF-токен и принятие условий; в продукте нужна атрибуция (CC-BY-4.0);
- на машине без ускорителя длинный VOD обрабатывать непрактично → стадия объявляется опциональной и пропускается с предупреждением ([§62](#62-переносимость-и-профили-исполнения)).

## 9. SCENE DETECTION

Инструменты: PySceneDetect, FFmpeg, собственный анализ смены кадров.

Каждая сцена: `start`, `end`, `duration` + metadata.

```json
{ "scene_id": 17, "start": 532.1, "end": 612.8 }
```

**Оговорка по геймплею.** Детектор `content` на динамичных играх срабатывает на каждый резкий поворот камеры и выдаёт тысячи ложных сцен. Нужны adaptive-детектор и минимальная длина сцены. На гейминге ценность сцен ниже, чем на IRL/Just Chatting — вес этого сигнала должен быть настраиваемым, а не фиксированным.

## 10. AUDIO ANALYSIS

Отдельный модуль. Определяет: громкость, резкие изменения громкости, крики, смех, эмоциональные всплески, тишину, длинные паузы, музыку, аплодисменты, необычные звуки.

Стек — комбинированный, не одна модель:

- **PANNs (CNN14)** или **YAMNet** — теги AudioSet. Классы Laughter, Screaming, Cheering, Applause, Music — это ровно то, что нужно, и работает лучше самописных эвристик. Код Apache-2.0, веса CC-BY-4.0.
- **librosa** — RMS, спектральные признаки, темп.
- **VAD** — речь/не речь.
- собственные эвристики поверх.

Отдельный выход, который обязателен: **признак наличия музыки** — используется как штраф при отборе клипа, см. [§59](#59-звук-на-экспорте).

## 11. ПОИСК ИНТЕРЕСНЫХ МОМЕНТОВ

Центральная часть проекта.

**Нельзя** делать простую систему «отправить весь transcript в LLM и спросить, где интересно».

Многоступенчатая воронка: дешёвые алгоритмы создают кандидатов, дорогой AI анализирует только кандидатов.

```text
VIDEO → TRANSCRIPT → SCENES → AUDIO EVENTS → CHAT EVENTS
      → EMOTION EVENTS → POTENTIAL MOMENTS → LLM ANALYSIS → FINAL SCORE
```

Численные ориентиры воронки (значения — из конфига, не из кода):

```text
8 часов VOD → ~150 потенциальных событий → ~30 кандидатов → 10–30 Shorts
```

## 12. CLIP SCORE

Единая схема. В v1 существовали две несовместимые (здесь и в [§38](#38-качество)) — они объединены.

```json
{
  "clip_id": "vod123_c07",
  "source_video_id": "vod123",
  "start": 753.0,
  "end": 821.4,
  "score_schema_version": 2,
  "interest_score": 0.87,
  "factors": {
    "semantic": 0.92,
    "emotion": 0.95,
    "audio": 0.87,
    "visual": 0.70,
    "context": 0.98,
    "completeness": 0.90,
    "novelty": 0.88
  },
  "penalties": {
    "music_present": 0.30,
    "unresolved_ending": 0.00
  },
  "signals": {
    "chat_rate_peak": 14.2,
    "audio_tag": "laughter",
    "scene_id": 17
  },
  "explanation": "Стример проигрывает на последней секунде, реакция друга, чат взрывается"
}
```

Правила:

- диапазон везде `0.0–1.0`, никаких смешанных шкал;
- `interest_score` — **производная** от `factors` и `penalties` по весам из конфига, а не независимое число;
- веса живут в `config.yaml` и версионируются вместе со схемой (`score_schema_version`);
- поле `explanation` обязательно — без объяснения score бесполезен для отладки;
- поле `signals` хранит сырые сигналы, породившие кандидата, для последующего анализа.

Название `interest_score` вместо `viral_score` из v1 — намеренно, см. [§54](#54-важное-ограничение).

## 13. ЧТО ИИ ДОЛЖЕН ИСКАТЬ

Смешные моменты, неожиданности, сильные реакции, крики, победы, поражения, конфликты, споры, важные игровые моменты, необычные ситуации, мемные моменты, эмоциональные моменты, кульминации, истории с началом и концом.

AI обязан отличать **интересно зрителю** от **просто громко**. Громкий крик без контекста получает низкий score.

## 14. ПОИСК НАЧАЛА КЛИПА

AI определяет начало сам. Нельзя брать `event_time − 10 секунд`.

Начало должно быть смысловым — там, где зритель получает контекст:

```text
«Ребята, сейчас я попробую убить босса...»  ← начало
   ↓ действие
   ↓ кульминация
   ↓ реакция
   ↓ конец
```

Выполняется в стадии LLM ([§4](#4-общая-архитектура)), до расчёта финального score.

---

## 15. ПОИСК КОНЦА КЛИПА

Конец включает завершение события. Не обрывать фразу, не заканчивать на «Я сейчас...».

Конец — после punchline, реакции, результата, завершения истории или естественной паузы.

Признак незавершённости фиксируется как штраф `unresolved_ending` в [§12](#12-clip-score).

---

## 16. УДАЛЕНИЕ ЛИШНЕГО

Находить и удалять: тишину, длинные паузы, загрузки, AFK, меню, инвентарь, повторения, бессмысленные перемещения, технические моменты, длинные участки без действия.

**Но:** не удалять паузы, являющиеся частью комедии или драматургии. Решение принимается с учётом контекста.

Технически это не «вырезание», а построение списка правок — см. [§56](#56-единая-ось-времени-edl). Любое удаление сдвигает всё, что идёт после, поэтому субтитры и трекинг обязаны считаться через отображение времени, а не по исходным таймкодам.

## 17. VERTICAL VIDEO

Формат 9:16, например 1080×1920. Инструменты: OpenCV, MediaPipe, детектор объектов, tracking, FFmpeg.

AI определяет: лицо, человека, персонажа, основной объект, игровую action area. Камера следует за главным объектом. **Простой статичный center crop запрещён.**

### Детектор объектов — интерфейс, не библиотека

Поддерживаются три взаимозаменяемых бэкенда, выбор — после сравнения на реальных видео:

| Бэкенд | Лицензия | Сильная сторона |
|---|---|---|
| MediaPipe | Apache-2.0 | лица и поза, быстро, работает на CPU |
| YOLOX | Apache-2.0 | люди и объекты, коммерчески чистый |
| Ultralytics YOLO | AGPL-3.0 / Enterprise | обычно лучшее качество из коробки, удобный API |

Реализация — `ObjectDetector` с тремя реализациями, переключение через `config.yaml`, см. [§43](#43-plugin-architecture).

Критерии финального выбора: точность на своём материале, скорость, **и лицензия**. Последнее становится решающим только при публичном запуске: если побеждает Ultralytics и проект идёт в SaaS — нужна Enterprise-лицензия либо переключение бэкенда. Пока инструмент личный — ограничений нет.

Раскладки кадра и правила движения камеры — [§61](#61-вертикальный-кадр).

## 18. СУБТИТРЫ

## 19. SHORTS

Для каждого автоматически: clip, vertical crop, subtitles, title, description, hashtags.

## 20. LONG FORM COMPILATION

Отдельный pipeline:


Цель — не склейка кусков, а логичная структура:

1. Hook
2. Setup
3. Development
4. Escalation

## 25. LLM

Архитектура допускает замену LLM без переписывания приложения. Интерфейс — `LLM_PROVIDER`.

Варианты: локальные Qwen / Llama / Mistral, OpenAI API, Anthropic API, Gemini API, другие OpenAI-совместимые API.

Основная архитектура не зависит от одного поставщика.

**Дефолт — внешний API, но это именно дефолт, а не архитектурное решение.** На машине без ускорителя локальная LLM выдаёт единицы токенов в секунду: для батча приемлемо, для итеративной отладки промптов нет. На машине с достаточной видеопамятью локальный провайдер включается одной строкой конфига, без изменений в коде. Оба пути равноправны и живут за одним интерфейсом.

### Три особенности API, которые сильно влияют на стоимость и качество

1. **Пакетная обработка.** Анализ кандидатов не чувствителен к задержке — это шаг внутри многочасового пайплайна. Пакетный режим (Message Batches) даёт **скидку 50%** при обработке в течение часа-суток. Отдельные интерактивные вызовы для этого сценария — переплата вдвое ни за что.
2. **Кэширование общего префикса.** Таксономия виральности, правила отбора и схема ответа одинаковы для всех кандидатов одного VOD. Вынесенные в стабильный префикс с меткой кэширования, они тарифицируются примерно в 0.1 от обычной цены при повторных вызовах. Ключевое требование: **префикс должен быть побайтово одинаковым** — никаких дат, идентификаторов и случайных значений внутри него, иначе кэш не срабатывает молча.
3. **Структурированный вывод.** Схема кандидата ([§12](#12-clip-score)) описывается как JSON Schema и передаётся в параметре формата вывода — модель не может вернуть невалидный JSON. Это снимает целый класс кода: ручные парсеры, повторные запросы при ошибке разбора, регулярные выражения по ответу.

### Оценка стоимости LLM на один 8-часовой VOD

~150 кандидатов, у каждого сжатое окно транскрипта (~500 токенов) поверх общего кэшированного префикса, ответ ~300 токенов:

| Вариант | Без пакетного режима | С пакетным режимом |
|---|---|---|
| Старшая модель | ~$1.6 | **~$0.8** |
| Средняя модель | ~$0.7 | **~$0.35** |

Порядок величин; проверить замером. **Вывод, важный для [§26](#26-экономия-и-качество-контекста): LLM в этом пайплайне дешевле аренды GPU.** Оптимизировать надо GPU-часы и хранение, а качество отбора моментов ([§53](#53-приоритеты), приоритет №1) не приносить в жертву экономии на токенах.

### Начальный выбор

Начинать со старшей модели: качество отбора — приоритет №1, а разница в стоимости на фоне аренды GPU незначительна. Понижать класс модели — осознанное решение после того, как накопятся данные ([§63](#63-сбор-данных-о-результатах-клипов)) и станет видно, теряется ли качество.

Оговорка по переносимости: пакетный режим и кэширование есть не у всех провайдеров и не на всех площадках. Интерфейс `LLM_PROVIDER` обязан работать и без них — с ними это оптимизация, без них рабочий путь.

## 26. ЭКОНОМИЯ И КАЧЕСТВО КОНТЕКСТА

Не отправлять полный 8-часовой transcript в LLM.

```text
8 часов → локальные дешёвые сигналы → кандидаты → сжатый transcript
        → LLM анализирует только кандидатов → финальный выбор
```

**Уточнение против v1.** Главная причина — **не деньги, а качество**. Полный транскрипт 8 часов это ~60–70 тыс. слов, порядка 150–200 тыс. токенов для русского, то есть единицы долларов на хорошей модели — не катастрофа. Но на контексте такого размера модель теряет детали и начинает выдавать произвольные куски, то есть ровно то, что запрещено в [§39](#39-нельзя-делать).

Реальные деньги уходят в GPU-часы и хранение, а не в токены — оптимизировать надо это, см. [§29](#29-режимы-стоимости) и [§67](#67-наблюдаемость-и-учёт-стоимости).

## 27. LOCAL-FIRST

Принцип: веса моделей свои, поставщик не диктует условия, open-source используется максимально широко.

Предпочтительный стек: WhisperX, faster-whisper, PyTorch, FFmpeg, OpenCV, PySceneDetect, MediaPipe / YOLOX / Ultralytics ([§17](#17-vertical-video)), pyannote, librosa, PANNs, Qwen / Llama / Mistral.

Честная оговорка: local-first полностью выполняется для аудио- и видеомоделей. Для LLM на старте используется внешний API — см. [§25](#25-llm). Платные API остаются опциональными и заменяемыми.

## 28. ПРОИЗВОДИТЕЛЬНОСТЬ

Стадии абстрагированы от устройства. Поддерживаются:

- **CPU** — локальная разработка;
- **NVIDIA CUDA** — арендованные инстансы для реальных прогонов;
- **ROCm** — официально не поддерживается: у CTranslate2 (движок faster-whisper и WhisperX) нет ROCm-бэкенда в апстриме. Существует сторонний форк `CTranslate2-rocm`; допустим как эксперимент, но не как основной путь.

Параметры конфигурации: `device`, `gpu_device`, `model_size`, `batch_size`, `compute_type`.

Подробности профилей и измеренные цифры — [§62](#62-переносимость-и-профили-исполнения).

## 29. РЕЖИМЫ СТОИМОСТИ

При локальных моделях основная стоимость — GPU, CPU, RAM, SSD, хранение видео. WhisperX, FFmpeg, OpenCV и большая часть стека не требуют оплаты API.

Два режима:

| Режим | Смысл |
|---|---|
| `COST_OPTIMIZED` | максимум локальных моделей, минимум внешних вызовов |
| `QUALITY_MAX` | допускает коммерческие API там, где они дают выигрыш |

## 33. FRONTEND

Интерфейс — не витрина поверх готовой системы, а способ ею пользоваться. [§51](#51-главная-цель) обещает не только «вставил URL и получил результат», но и «человек может проверить и исправить решения AI перед публикацией». Вторая половина этого обещания целиком живёт в интерфейсе: подвинуть границу клипа на полсекунды, посмотреть превью, поправить область кадра — задачи по своей природе визуальные, через командную строку они не решаются.

**Стек: React + Vite + TypeScript.** Выбран из-за редактора клипа ([§36](#36-manual-edit)): покадровая перемотка, таймлайн с волной, перетаскивание границ и области кадра, живое превью стиля субтитров. Это единственная часть системы, где серверный рендеринг заметно проигрывает.

**Принцип:** UI работает поверх того же публичного API, что и CLI. Ни одной операции, доступной только из интерфейса, и ни одной — только из консоли.

### Страницы и очерёдность

| Приоритет | Страница | Содержание |
|---|---|---|
| **1** | Запуск и обработка | URL или файл → START; прогресс по стадиям в реальном времени; время и стоимость ([§67](#67-наблюдаемость-и-учёт-стоимости)) |
| **1** | Обзор клипов | Найденные моменты: превью, score, объяснение, тип; Accept / Reject ([§35](#35-clip-review)) |
| **2** | Редактор клипа | Границы, область кадра, субтитры, заголовок, описание, хэштеги ([§36](#36-manual-edit)) |
| **2** | Ввод результатов | Ручной ввод метрик опубликованных клипов ([§63](#63-сбор-данных-о-результатах-клипов)) |
| **3** | Проекты и дашборд | Список видео, сводка, история обработки ([§34](#34-dashboard)) |
| **3** | Экспорты | Готовые файлы, повторный рендер |
| **3** | Настройки | Конфигурация ([§46](#46-конфигурация)), пресеты субтитров, профиль исполнения |

Технические требования — [§69](#69-интерфейс-технические-требования).

## 35. CLIP REVIEW

Пользователь просматривает найденные моменты:

```text
CLIP #1   Score: 0.87   Type: Funny

[Preview]  [Accept]  [Reject]  [Edit]
```

## 37. EXPORT

FFmpeg.

| Профиль | Параметры |
|---|---|
| Short | 1080×1920, H.264, AAC, MP4 |
| Long YouTube | 1920×1080, H.264, AAC, MP4 |

Обязательные параметры, отсутствовавшие в v1:

- `-pix_fmt yuv420p` — иначе часть плееров и платформ не примут файл;
- `-movflags +faststart` — для веб-воспроизведения;
- явный CRF или битрейт (не полагаться на дефолт);
- нормализация громкости — [§59](#59-звук-на-экспорте);
- FPS настраивается.

**Точность нарезки.** Копирование потока (`-c copy`) режет по ключевым кадрам, ошибка до нескольких секунд — для клипов неприемлемо. Финальные клипы режутся с перекодированием. Для скорости — быстрый seek перед `-i` плюс точный досдвиг.

## 41. TWITCH CHAT

**Перенесено с этапа 6 на этап 2.** Обоснование: это самый дешёвый из сильных сигналов, считается на CPU и напрямую работает на приоритет №1 ([§53](#53-приоритеты)).

Всплеск сообщений — сигнал интересного момента:

```text
«HAHAHAHA»  «OMG»  «WHAT»  «NO WAY»  → рост частоты сообщений → кандидат
```

Полезные признаки: частота сообщений в секунду, всплеск относительно скользящего среднего, доля эмоций/эмодзи, повторяющиеся паттерны (`KEKW`, `OMEGALUL`), задержка реакции чата относительно события (обычно 1–3 секунды — учитывать при выравнивании).

Оговорка: chat replay доступен через неофициальный эндпоинт (или TwitchDownloaderCLI) — источник хрупкий, обернуть и предусмотреть деградацию без него.

## 43. PLUGIN ARCHITECTURE

Подключаемые анализаторы со стандартным интерфейсом: `GameAnalyzer`, `ChatAnalyzer`, `AudioAnalyzer`, `FaceAnalyzer`, `SceneAnalyzer`, `ObjectDetector`.

Каждый анализатор:

- объявляет требования к устройству (CPU / GPU);
- возвращает сигналы в едином формате, пригодном для [§12](#12-clip-score);
- может быть отключён без поломки pipeline.

`ObjectDetector` с тремя бэкендами ([§17](#17-vertical-video)) — первый практический пользователь этого механизма.

## 44. AI PIPELINE

Компонентная структура, согласованная с [§4](#4-общая-архитектура):

```text
Video
  ↓ VideoMetadataExtractor
  ↓ AudioExtractor
  ↓ WhisperX                    ─┐
  ↓ SceneDetector                │ по всему VOD
  ↓ AudioAnalyzer                │
  ↓ ChatAnalyzer (Twitch)       ─┘
  ↓ CandidateGenerator          → 100–200 кандидатов
  ↓ LLMAnalyzer + ClipBoundaryOptimizer   ← границы уточняются здесь
  ↓ ClipScorer                  → отбор top-N
  ↓ Diarization (опционально, только по выбранным)
  ↓ SilenceRemover              → EDL (§56)
  ↓ VisionAnalyzer + VerticalCropper      ← только по выбранным клипам
  ↓ SubtitleGenerator                     ← через EDL
  ↓ ShortRenderer  ·  CompilationBuilder
  ↓ MetadataGenerator
  ↓ Exporter
```

Отличия от v1: `VisionAnalyzer` и `Diarization` спустились ниже отбора кандидатов; `ClipBoundaryOptimizer` поднялся к `LLMAnalyzer`; добавлены `ChatAnalyzer` и `SilenceRemover`.

# НОВЫЕ РАЗДЕЛЫ (v2)

## 56. ЕДИНАЯ ОСЬ ВРЕМЕНИ (EDL)

**Проблема.** Удаление тишины и пауз ([§16](#16-удаление-лишнего)) сдвигает всё, что идёт после каждой вырезки. Субтитры, word timestamps, траектория кропа и timestamps в описании считаются в исходном времени VOD. Если не ввести явное преобразование, субтитры разъедутся с речью — и это будет обнаружено только глазами, на готовом ролике.

**Решение.** Единственный источник истины о времени — **EDL** (edit decision list): список сохраняемых интервалов исходного видео.

```json
{
  "clip_id": "vod123_c07",
  "segments": [
    { "src_start": 753.0, "src_end": 768.4 },
    { "src_start": 771.9, "src_end": 821.4 }
  ]
}
```

Правила, обязательные к соблюдению:

1. Ни один компонент после `SilenceRemover` не работает с исходными таймкодами напрямую.
2. Существует пара функций `to_output(src_t)` и `to_source(out_t)`, и только они выполняют преобразование.
3. Субтитры, траектория кропа и timestamps описания генерируются **в выходном времени**.
4. EDL сохраняется в `storage/.../edl/edl.json` и является артефактом стадии — его можно посмотреть и продиагностировать отдельно.
5. Слово, попадающее на границу вырезки, не разрывается: вырезка сдвигается к ближайшей паузе.

## 57. НАДЁЖНОСТЬ STT

На музыке, игровом звуке и длинной тишине Whisper устойчиво **выдумывает текст** — обычно повторяющиеся фразы или титры вроде «Субтитры сделал DimaTorzok». На стриме, где почти всегда играет музыка и звучит игра, это не редкий случай, а норма. Ложный транскрипт напрямую отравляет [§11](#11-поиск-интересных-моментов).

Обязательные меры:

1. **VAD-гейтинг** — не транскрибировать участки без речи.
2. **Отсев по метрикам сегмента** — `no_speech_prob` выше порога, `avg_logprob` ниже порога → сегмент помечается недостоверным.
3. **Детектор повторов** — одинаковые n-граммы подряд — типичный признак галлюцинации.
4. **Чёрный список фраз** — типовые галлюцинации (титры, «Продолжение следует», реклама).
5. **Флаг достоверности в артефакте** — не удалять молча, а помечать: удаление затрудняет отладку.

Помеченные сегменты не участвуют в отборе кандидатов и не попадают в субтитры.

## 58. ИДЕМПОТЕНТНОСТЬ И КЭШ СТАДИЙ

Обработка 8 часов будет падать — по OOM, по сети, по драйверу, по истечении аренды GPU. Перезапуск с нуля неприемлем: транскрипция стоит десятки минут GPU-времени.

Правила:

1. Каждая стадия — чистая функция «артефакты на входе → артефакты на выходе», без скрытого состояния.
2. Ключ кэша = хэш(входные артефакты + версия конфига стадии + версия кода стадии). Совпал — стадия пропускается.
3. Стадия запускается изолированно: `narezka run <stage> --video-id X`.
4. Запись артефакта атомарна: во временный файл, затем переименование. Иначе прерванная стадия оставляет полуфайл, который кэш примет за готовый.
5. Артефакты самодостаточны: стадию можно выполнить на другой машине, скопировав только её входы.

Пункты 3 и 5 — не удобство, а требование: они делают возможной работу на арендованном GPU ([§62](#62-переносимость-и-профили-исполнения)).

## 59. ЗВУК НА ЭКСПОРТЕ

### Громкость

Клипы берутся из разных участков стрима и различаются по громкости. Без нормализации это самый заметный признак низкого качества нарезки.

Применять EBU R128 (`loudnorm`), целевое значение около **−14 LUFS**, с ограничением true peak. Значение — в конфиге (`output.loudness_target_lufs`), потому что рекомендации платформ различаются.

Нормализация выполняется **после** сборки клипа по EDL, а не до.

### Музыка и Content ID

Фоновая музыка в стриме приводит к блокировке или потере монетизации ролика. Детектор музыки уже есть в [§10](#10-audio-analysis) — нужно применить его результат:

- доля музыки в интервале кандидата → штраф `music_present` в [§12](#12-clip-score);
- при высокой доле — пометка клипа «риск Content ID» в Clip Review;
- разделение дорожек и подавление музыки — возможное развитие, не в MVP.

Это дешёвая мера, заметно повышающая долю пригодных к публикации нарезок.

## 60. СУБТИТРЫ: ТЕХНИЧЕСКАЯ РЕАЛИЗАЦИЯ

**Формат.** ASS/libass через FFmpeg. Подсветка текущего слова — теги `\k`. Альтернатива (рендер PNG-оверлеев) даёт больше свободы в оформлении ценой скорости и сложности; выбор фиксируется при реализации, интерфейс генератора субтитров от него не зависит.

**Safe zones.** Интерфейс TikTok, Shorts и Reels перекрывает часть кадра: снизу примерно 20–25% (подписи, кнопки, описание) и правый край (панель действий). Субтитры и ключевое действие туда попадать не должны. Конкретные значения вынести в конфиг стиля — они меняются вместе с приложениями платформ.

**Шрифты.** Нужен шрифт с полным покрытием кириллицы и лицензией, разрешающей встраивание и коммерческое использование. Шрифт фиксируется в репозитории вместе с лицензией — иначе на другой машине субтитры отрендерятся другим шрифтом или квадратами.

**Разбиение.** Опираться на word timestamps и паузы, а не на равные интервалы: строка не должна разрывать смысловую группу. Ограничения — максимум символов в строке и максимум строк, из пресета стиля.

**Время.** Субтитры генерируются в выходном времени через EDL ([§56](#56-единая-ось-времени-edl)).

## 61. ВЕРТИКАЛЬНЫЙ КАДР

### Раскладки

Одного «следования за объектом» недостаточно. Поддержать несколько раскладок и выбирать по содержимому:

| Раскладка | Когда применяется |
|---|---|
| Слежение за объектом | одно лицо/объект в кадре |
| Сплит: геймплей сверху, вебка снизу | есть вебка и важен геймплей |
| Картинка-в-картинке | вебка второстепенна |
| Блюр-подложка с исходным кадром по центру | ничего не выделяется, но резать жалко |

### Обрезка по бокам и размер содержимого — один параметр

Это не две настройки, а две проекции одной. Исходник вписывается по ширине кадра, поэтому чем уже он после обрезки, тем выше выглядит в вертикальном кадре. Отрезать нечего — содержимое занимает узкую полосу посреди подложки; отрезать много — содержимое заполняет кадр, но края теряются безвозвратно.

Для 16:9 в 9:16 (реальные числа фикстуры 1024×576 → 1080×1920):

| Вариант | Срез по бокам | Видно по высоте |
|---|---|---|
| `full` | 0% | 32% |
| `balanced` | 25% | 42% |
| `focus` | 50% | 63% |
| `fill` | 68% | 100%, полос нет |
| `custom` | задаётся вручную | считается |

Величина среза для `fill` зависит от пропорций исходника и вычисляется, а не задаётся константой: у 4:3 и у 21:9 она разная.

**Что настраивается:** вариант обрезки, точка привязки (`center` / `left` / `right`), чем заполнены полосы (размытый кадр или однотонная заливка), сила размытия — ноль отключает его, оставляя резкую подложку.

Настройки хранятся отдельным файлом на видео (`meta/framing.json`) поверх конфига: подходящее кадрирование зависит от конкретной записи, у стрима с вебкой в углу и у записи экрана оно разное. Файл входит в ключ кэша стадии render — правка настройки перерендеривает ролики, отсутствие правки оставляет их из кэша.

**Это не нарушает запрет [§39](#39-анти-паттерны) на статичный центральный кроп:** величина обрезки задаётся пользователем и может быть нулевой, а точка привязки выбирается. Автоматический выбор области по содержимому — этап 4, он заменит ручную привязку значением `auto`, а не отменит настройку.

### Два правила построения графа фильтров

Куплены отладкой, а не выведены из документации:

1. **Ни одной ветки из независимого источника.** Однотонные полосы делает `pad`, а не `color` + `overlay`: источник `color` идёт по своим меткам времени, и на коротком отрезке `overlay` успевает выдать первый кадр раньше, чем подъедет кадр видео — в результат попадает одна заливка. Все ветки графа должны расти из `[0:v]`.
2. **Подложка не строится, когда её не видно.** При заполненном кадре размытие всё равно перекрыто содержимым — считать его значит впустую тратить время кодирования.

### Оптимизация: вебка статична

Прямоугольник вебкамеры на стриме почти всегда неподвижен. Искать его **один раз на VOD**, а не покадрово в каждом клипе. Это убирает основную часть работы детектора и заодно делает результат стабильным.

### Движение камеры

Резкие скачки рамки укачивают сильнее, чем плохое кадрирование:

1. Сглаживание траектории — EMA или фильтр Калмана.
2. Мёртвая зона: не двигать камеру, пока объект не вышел за порог.
3. На смене сцены — **рез, а не панорама**.
4. Ограничение максимальной скорости панорамирования.
5. Детекция не на каждом кадре: 5–10 fps плюс интерполяция между ними.

## 62. ПЕРЕНОСИМОСТЬ И ПРОФИЛИ ИСПОЛНЕНИЯ

### Главное требование

**Программа не пишется под конкретный процессор или видеокарту.** Один и тот же код запускается и работает:

- на ноутбуке без дискретной видеокарты;
- на машине с NVIDIA;
- на арендованном GPU-инстансе;
- в контейнере на сервере.

Разница между этими средами — только в скорости и в размере используемых моделей, но не в наличии функциональности и не в правках кода.

### Как это обеспечивается

1. **Автоопределение устройства.** `device: auto` — дефолт. Порядок проверки: CUDA → прочие ускорители → CPU. Явное значение (`cpu`, `cuda`) переопределяет автоопределение.
2. **Никаких обязательных ускорителей.** CPU — всегда работающий путь. Любая стадия обязана иметь CPU-реализацию; если у стадии её нет, стадия объявляется опциональной и pipeline корректно работает без неё ([§43](#43-plugin-architecture)).
3. **Модель подбирается под доступную память, а не прибивается гвоздями.** Размер модели STT, размер батча и `compute_type` берутся из профиля; профиль может выбираться автоматически по доступным ресурсам.
4. **Мягкая деградация вместо отказа.** Нет GPU — берётся меньшая модель, диаризация пропускается, детектор переключается на CPU-совместимый бэкенд. Пользователь получает предупреждение, а не ошибку.
5. **Никаких зашитых путей и имён устройств.** Всё через конфиг ([§46](#46-конфигурация)).
6. **Проверка ресурсов перед запуском стадии** — свободная память, место на диске, доступность бинарников. Понятное сообщение вместо падения в середине восьмичасовой обработки.

### Профили

Профиль — это пресет «скорость против качества», а не описание конкретного железа. Оба профиля запускаются на любой машине; отличается время выполнения.

| | `dev` | `batch` |
|---|---|---|
| Назначение | цикл разработки, быстрая обратная связь | реальные прогоны |
| Материал | короткие фикстуры (5–10 мин) | полные VOD |
| STT | `small` int8 — обоснование в замерах ниже | `large-v3` |
| Диаризация | выключена | включена |
| CV | упрощённый режим | полный |
| LLM | через API | по конфигу |

`profile: auto` допустим: если доступного ускорителя нет и материал короткий — `dev`, иначе `batch`.

### Кэш стадий как основа переносимости

С кэшем ([§58](#58-идемпотентность-и-кэш-стадий)) тяжёлая стадия считается один раз и переиспользуется. Это работает в обе стороны:

- на слабой машине повторные запуски pipeline не пересчитывают транскрипт;
- тяжёлую стадию можно выполнить на мощной машине, забрать артефакт и продолжить на слабой.

Артефакты анализа (`transcript/`, `analysis/`) — единицы мегабайт, переносятся легко. Исходное видео между машинами не копируется: на второй машине оно скачивается заново через yt-dlp — быстрее и дешевле передачи десятков гигабайт.

Именно поэтому [§47](#47-development-roadmap) этап 0 (скелет стадий с кэшем) стоит первым: без него разработка на слабом железе невозможна, а сильное железо нельзя подключить по требованию.

### Справочные замеры

`faster-whisper` int8, RTF (меньше единицы = быстрее реального времени):

| Модель | Ноутбучный 6-ядерный CPU | Десктопный многоядерный CPU | Современный GPU |
|---|---|---|---|
| `base` | **0.08–0.12** (замерено) | ~0.05 | ≪0.05 |
| `small` | **0.28** (замерено) | ~0.15 | ≪0.05 |
| `large-v3-turbo` | ~1 | ~0.5 | ~0.02 |
| `large-v3` | ~4–6 | ~2.5–3 | ~0.02–0.03 |

Значения для `base` замерены на фикстурах (Ryzen 5 7535HS, 6 ядер): 66 секунд речи за 7.6 с, 379 секунд за 28.4 с. Остальные строки — оценки, уточняются по мере замеров.

**Скорость не единственный критерий — и не главный.** Сравнение на одной фикстуре с русской речью, один и тот же фрагмент:

| Модель | RTF | Что распознано |
|---|---|---|
| `base` | 0.12 | «**80 лица** всегда хорошо… расписывает **пографику**… **листи в наклёнах**» |
| `small` | 0.28 | «**Осень в столице** всегда хороша… расписывает **по графику** ясные дни» |

`base` втрое быстрее, но выдаёт текст, по которому невозможно судить о содержании. Причём уверенность сегмента остаётся высокой — фильтр [§57](#57-надёжность-stt) такие случаи не ловит и не должен: это не галлюцинация, а неверное распознавание. Проверять на таком тексте отбор моментов бессмысленно.

Отсюда: **в профиле `dev` стоит `small`.** Двадцать лишних секунд на минуту звука ничего не решают, разборчивый текст решает всё.

Выводы, верные для любой машины без ускорителя: `large-v3` на CPU непригоден для длинных видео; для коротких фикстур подходят `base` и `small`; полные VOD обрабатываются там, где есть ускоритель.

**Ориентир по стоимости** (8-часовой VOD на арендованном GPU уровня RTX 4090): около 1–2 GPU-часов суммарно, порядка $0.3–1.0 аренды плюс хранение. Основные статьи — транскрипция (10–20 мин), детекция сцен (10–20 мин CPU), диаризация (20–50 мин, если по всему VOD — поэтому её ограничивают), рендер (20–40 мин CPU или кратно меньше на аппаратном кодировании).

### Среда разработки

Целевая версия Python — **3.12**. Причина не в предпочтениях, а в готовности зависимостей: часть ключевых пакетов (в частности MediaPipe) на момент проверки не публикует колёса для 3.13. Версия фиксируется в проекте, чтобы окружение воспроизводилось одинаково на любой машине.

Внешние бинарники: `ffmpeg` и `ffprobe` обязательны, наличие проверяется при старте. В контейнере они поставляются вместе с образом, локально — устанавливаются системно.

## 63. СБОР ДАННЫХ О РЕЗУЛЬТАТАХ КЛИПОВ

Реализация [§40](#40-обучение-на-результатах). Способ обучения — на собственных данных: показатели опубликованных клипов вносятся вручную, впоследствии автоматизируются.

### Таблица `clip_performance`

| Поле | Смысл |
|---|---|
| `clip_id` | ссылка на клип |
| `platform` | youtube / tiktok / instagram |
| `published_at` | дата публикации |
| `views`, `likes`, `comments`, `shares`, `retention`, `ctr` | фактические показатели |
| `measured_at` | когда сняты метрики (обязательно: 1000 просмотров за день и за месяц — разные результаты) |
| `factors_snapshot` | **вектор `factors` на момент публикации, неизменяемый** |
| `score_schema_version` | версия схемы score |
| `prompt_version` | версия промпта отбора |

Без `factors_snapshot` цифры просмотров ничему не учат: непонятно, какие признаки сработали. Без версий через месяц не восстановить, на какой версии системы получен результат.

### Ввод данных

- **Ручной ввод** — форма рядом с Clip Review ([§35](#35-clip-review)). Минимум трения, иначе данные не заносятся.
- **Accept / Reject** — записываются автоматически при обычной работе. Это быстрый сигнал: он копится с первого дня, тогда как метрики просмотров приходят через недели. Оба идут в один механизм.
- **Ручная правка границ** ([§36](#36-manual-edit)) — величина и направление сдвига показывают систематическую ошибку определения границ.
- **Автоматизация позже** — YouTube Analytics API и TikTok API отдают метрики сами; ручной ввод остаётся запасным путём.

### Использование

Накопленные данные применяются к весам в [§12](#12-clip-score) — сначала как ручная калибровка на основе наблюдений, затем, при достаточном объёме, как обучаемая модель. Любое изменение весов повышает `score_schema_version`.

## 64. ОЧЕРЕДИ, GPU И РЕСУРСЫ

- Две очереди: `cpu` и `gpu`. Стадия объявляет, какая ей нужна ([§43](#43-plugin-architecture)).
- На GPU-стадиях — семафор: один GPU обслуживает одну задачу за раз, иначе OOM.
- Долгие стадии периодически сообщают прогресс, иначе задача выглядит зависшей.
- Таймаут и ограничение числа повторов на стадию; повтор безопасен благодаря [§58](#58-идемпотентность-и-кэш-стадий).
- Отмена задачи должна корректно убивать дочерний процесс FFmpeg, а не оставлять его сиротой.

## 65. RETENTION И БЮДЖЕТ ДИСКА

Порядок величин на один 8-часовой VOD:

| Артефакт | Размер |
|---|---|
| Исходное видео 1080p60 | 15–30 ГБ |
| `audio.wav` 16 кГц моно | ~0.9 ГБ (FLAC — примерно вдвое меньше) |
| Транскрипт и анализ | единицы МБ |
| Готовые Shorts | десятки МБ |

Правила:

1. Исходное видео удаляется после того, как все зависящие от него стадии завершены и клипы отрендерены. Это единственный крупный потребитель диска.
2. `retention_until` в таблице `videos` — поле заложено сразу ([§31](#31-database)).
3. Перед скачиванием проверять свободное место: падение на 90% восьмичасовой загрузки из-за переполнения диска — обидная и полностью предотвратимая ошибка.
4. Промежуточные нарезки в `clips/` удаляются после сборки финального ролика.

## 69. ИНТЕРФЕЙС: ТЕХНИЧЕСКИЕ ТРЕБОВАНИЯ

Обзор и состав страниц — [§33](#33-frontend). Здесь то, что определяет, будет интерфейсом приятно пользоваться или мучительно.

### Превью без полного рендера — главное архитектурное решение

Пользователь двигает границу клипа на полсекунды. Если каждая правка запускает FFmpeg и требует ждать минуту, работать невозможно, и никакое оформление этого не спасёт.

Решение: **в браузере проигрывается исходное видео с наложениями, рендер запускается только на экспорт.**

- воспроизведение исходника с нужного места через range-запросы;
- рамка вертикального кадра — накладывается поверх, не вжигается;
- субтитры — рисуются поверх по word-level timestamps, а не берутся из готового файла;
- удалённые участки — пропускаются при воспроизведении по EDL ([§56](#56-единая-ось-времени-edl)).

Из этого следует требование к серверу: раздача видео **обязана поддерживать range-запросы**, иначе браузер тянет весь файл перед началом воспроизведения.

### Прогресс в реальном времени

Обработка идёт минутами и часами. Опрос статуса раз в несколько секунд даёт ощущение зависшей системы.

- поток событий с сервера (SSE или WebSocket): смена стадии, проценты внутри длинных стадий, ошибки;
- состояние живёт на сервере, а не в памяти вкладки: перезагрузка страницы и возврат назавтра показывают ту же картину;
- никаких блокирующих модалок «подождите» — задача поставлена, вкладку можно закрыть.

### Клавиатура

Просмотр тридцати кандидатов мышкой — то, после чего систему бросают. Обзор клипов обязан управляться с клавиатуры:

| Клавиши | Действие |
|---|---|
| `J` / `K` / `L` | назад / пауза / вперёд, привычно по видеоредакторам |
| `←` `→` | перемотка по кадрам, с `Shift` — по секундам |
| `[` `]` | подвинуть начало / конец клипа |
| `A` / `R` | Accept / Reject и переход к следующему |
| `Space` | воспроизведение |

Именно это отличает «приятный интерфейс» от «интерфейс есть».

### Прочее

- **Тёмная тема по умолчанию.** Работа идёт с видео; светлый фон вокруг кадра мешает оценивать картинку.
- **Объяснение видно сразу.** Поле `explanation` из [§12](#12-clip-score) показывается рядом со score, а не прячется во всплывающей подсказке: пользователь должен понимать, почему AI выбрал этот момент, иначе он не может осмысленно нажать Reject.
- **Правка не теряется.** Ручные изменения границ переживают пересчёт стадии и не затираются повторным прогоном.
- **Мобильный экран** нужен для просмотра результата, но не для редактора — редактор рассчитан на десктоп.
