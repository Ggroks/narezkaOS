# Заметки по исходному проекту

**Источник:** <https://github.com/SamurAIGPT/AI-Youtube-Shorts-Generator> (MIT)
**Статус:** справочник, форк не делается — см. [BAZA.md §2](../BAZA.md#2-основа-проекта)
**Цель документа:** зафиксировать переиспользуемые идеи, чтобы больше не возвращаться к чужому коду.

Код оттуда **не копируется**. Если какой-то фрагмент всё же будет заимствован — MIT требует сохранить copyright notice, отметить это в карточке компонента.

## Что там есть

Структура: `main.py` (CLI) + `shorts_generator/` — `config.py`, `downloader.py`, `transcriber.py`, `highlights.py`, `clipper.py`, `pipeline.py`, `muapi.py`, `local/`.

Два режима: `--mode api` (через MuAPI — платный сервис автора, нам не нужен) и `--mode local` (yt-dlp + faster-whisper + FFmpeg/OpenCV + внешний LLM).

Их pipeline: download → transcribe → классификация типа контента → чанкинг длинного транскрипта → ранжирование хайлайтов через LLM → дедупликация → top-N → вертикальный рендер.

Чего там **нет**: субтитров, Twitch, детекции сцен, анализа аудио, диаризации, чата, БД, очереди задач, web UI, компиляций.

## Идея 1: таксономия виральности

Самое ценное. Готовый каркас для наших LLM-промптов ([BAZA §13](../BAZA.md#13-что-ии-должен-искать)) — восемь сигналов в порядке приоритета:

| # | Сигнал | Смысл |
|---|---|---|
| 1 | Hook moments | фразы, вызывающие любопытство |
| 2 | Emotional peaks | искреннее удивление, смех, уязвимость |
| 3 | Opinion bombs | поляризующие, контринтуитивные заявления |
| 4 | Revelation moments | факты, меняющие взгляд зрителя |
| 5 | Conflict / tension | несогласие, конфронтация |
| 6 | Quotable one-liners | самодостаточные цитаты |
| 7 | Story peaks | кульминация или разворот |
| 8 | Practical value | сразу применимый совет |

**Замечание при переносе.** Список заточен под подкасты и интервью. Для стримов и геймплея он покрывает не всё — у нас в [BAZA §13](../BAZA.md#13-что-ии-должен-искать) дополнительно: победы, поражения, крики, важные игровые моменты, мемные моменты, необычные ситуации. Практика: взять их восемь как базу, добавить свои игровые категории, и **обязательно** сохранить наше правило «интересно зрителю ≠ просто громко».

## Идея 2: чанкинг длинного транскрипта

| Параметр | Значение у них |
|---|---|
| Порог чанкинга | видео ≥ 1800 с (30 мин) |
| Размер окна | 1200 с (20 мин) |
| Перекрытие | 60 с |

Перекрытие нужно, чтобы момент на стыке окон не потерялся. Нам это понадобится, но с оговоркой: у нас в LLM идёт не сплошной транскрипт, а сжатые кандидаты ([BAZA §26](../BAZA.md#26-экономия-и-качество-контекста)), поэтому чанкинг применяется на **этапе порождения кандидатов**, а не на этапе LLM-анализа.

## Идея 3: дедупликация кандидатов

Хайлайты сортируются по score по убыванию; клип отбрасывается, если перекрывается более чем на 50% своей длительности с уже принятым клипом с более высоким score.

Простой и рабочий алгоритм. Берём как есть, порог 50% — в конфиг.

## Идея 4: классификация типа контента

Перед ранжированием LLM определяет тип: `podcast, interview, tutorial, lecture, commentary, debate, vlog, other` плюс уровень плотности (`low` — много воды, `medium`, `high` — плотная информация). Тип используется для подстройки промпта ранжирования.

**Расширить под нашу задачу:** добавить `gaming`, `just_chatting`, `irl`, `speedrun`. Плотность полезна и у нас — на стриме с низкой плотностью порог отбора кандидатов должен быть строже.

## Идея 5: ориентиры длительности клипа

| Параметр | Значение у них |
|---|---|
| Оптимум | 45–90 с |
| Минимум | 20 с (для удачной одной фразы) |
| Максимум | 180 с (когда нужен полный сюжет) |

У нас в [BAZA §19](../BAZA.md#19-shorts) заявлено 15–90 с. Их наблюдение про «минимум 20 с, но до 180 с ради полного сюжета» разумно: жёсткая верхняя граница обрезает истории. Сделать `min/optimal/max` тремя параметрами конфига, а не одним диапазоном.

## Идея 6: сглаживание при face tracking

В локальном режиме кроп 9:16 делается через OpenCV с детекцией лица и сглаживанием движения. Подтверждает необходимость мер из [BAZA §61](../BAZA.md#61-вертикальный-кадр): без сглаживания рамка дёргается.

## Идея 7: параметры VAD

Их дефолты для Silero VAD, полезны как отправная точка:

```text
threshold                 0.5
min_speech_duration_ms    250
max_speech_duration_s     inf
min_silence_duration_ms   2000
speech_pad_ms             400
```

`speech_pad_ms = 400` — важная деталь: без запаса речь обрезается на границах. `min_silence_duration_ms = 2000` для нас, вероятно, велико — при удалении пауз ([BAZA §16](../BAZA.md#16-удаление-лишнего)) понадобится меньший порог, настраиваемый отдельно.

## Чего оттуда брать нельзя

### Логика выбора клипов

Их схема: LLM читает транскрипт (целиком или чанками) и **сам возвращает таймкоды** `start_time` / `end_time` вместе со score.

Это ровно то, что запрещено в [BAZA §39](../BAZA.md#39-нельзя-делать). Проблемы:

1. Нет дешёвого предварительного отбора — дорогая модель обрабатывает весь материал.
2. Границы клипа определяются моделью, которая не слышала звук и не видела кадр: смех, крик и реакция чата ей недоступны.
3. На длинном контексте качество деградирует, отсюда и потребность в чанкинге.

У нас вместо этого: дешёвые сигналы по всему VOD → кандидаты → LLM только по кандидатам ([BAZA §11](../BAZA.md#11-поиск-интересных-моментов), [§4](../BAZA.md#4-общая-архитектура)).

### Схема score

У них `score` — одно число 0–100 от LLM, плюс `hook_sentence` и `virality_reason`.

У нас ([BAZA §12](../BAZA.md#12-clip-score)) — вектор `factors` с весами из конфига и производный `interest_score`. Причина: одно число от LLM невозможно отладить и невозможно калибровать по накопленным результатам ([BAZA §63](../BAZA.md#63-сбор-данных-о-результатах-клипов)).

Что взять: поля `hook_sentence` и `virality_reason` — хорошая идея. У нас аналог — обязательное `explanation`.

### Инфраструктура

Линейный CLI-скрипт без БД, очереди и восстановления после сбоя. Для 8-часовых VOD не подходит — см. [BAZA §58](../BAZA.md#58-идемпотентность-и-кэш-стадий).

### MuAPI

`muapi.py` и режим `--mode api` — платный сервис автора. Не используется.
